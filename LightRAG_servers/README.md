# LightRAG サーバ（ローカル検証環境）

社内文書を検索するための **LightRAG サーバ4台**。
`aiagent_minimal_rag_tougou` のアプリとは**完全に別のフォルダ・別のvenv**で動きます。
アプリはこの4台に **URLとAPIキー**だけで繋ぎます（実運用でIT部門から払い出される形と同じ）。

```
あなた（アプリの管理画面）
      │  URL と APIキーを手で入力
      ▼
アプリ（aiagent_minimal_rag_tougou）
      │  HTTP: POST /query/data（検索だけ。回答は書かせない）
      ▼
LightRAG サーバ ×4（このフォルダ）
      │
      ▼
OpenAI（索引作成・キーワード抽出・埋め込み）
```

## 払い出し情報

アプリの「ナレッジベース」画面に、この4件をそのまま入力してください。

| 名前 | URL | APIキー | 中身 |
|---|---|---|---|
| 設備マニュアル | `http://127.0.0.1:9621` | `key-manual-9621` | A・B・C装置の保全手順書、取扱説明書 |
| トラブル事例 | `http://127.0.0.1:9622` | `key-trouble-9622` | 過去の停止事例4件（原因・処置・復旧時間） |
| 改善事例 | `http://127.0.0.1:9623` | `key-kaizen-9623` | 実施した改善3件とその効果 |
| 作業標準 | `http://127.0.0.1:9624` | `key-standard-9624` | 初動の標準、MTTRの定義、記録要領 |

「説明」欄にはたとえば次のように書きます（**AIがこれを読んで調べ先を決めます**）。

| 名前 | 説明の例 |
|---|---|
| 設備マニュアル | 装置の保全手順・取扱説明・部品の仕様と交換周期。手順や仕様を調べるときに使う。 |
| トラブル事例 | 過去の設備停止の原因・処置・復旧時間の記録。似た事例を探すときに使う。 |
| 改善事例 | 実施した改善活動とその効果。再発防止策や過去の対策を調べるときに使う。 |
| 作業標準 | 作業のきまり。MTTRなど指標の定義もここにある。 |

## 使い方

```powershell
# 起動（4台。20〜40秒かかります）
powershell -ExecutionPolicy Bypass -File start-servers.ps1

# 状態の確認（healthy / キーが効いているか / 文書の件数）
powershell -ExecutionPolicy Bypass -File check-servers.ps1

# 停止
powershell -ExecutionPolicy Bypass -File stop-servers.ps1
```

各サーバは自分の管理画面も持っています（ブラウザで `http://127.0.0.1:9621` などを開く）。
文書の追加・削除・ナレッジグラフの確認はそちらからもできます。

## 4台の分け方

同じ実行ファイル・同じ `.env` を共有し、**違うのは3つだけ**です。

| | ポート | ワークスペース | APIキー |
|---|---|---|---|
| 設備マニュアル | 9621 | `manual` | `key-manual-9621` |
| トラブル事例 | 9622 | `trouble` | `key-trouble-9622` |
| 改善事例 | 9623 | `kaizen` | `key-kaizen-9623` |
| 作業標準 | 9624 | `standard` | `key-standard-9624` |

**ワークスペース**が保存先を分けます（`rag_storage/` の下に別々のフォルダができる）。
これがないと4台が同じ索引を共有してしまい、環境を分ける意味がなくなります。

**APIキーは `.env` に書いていません。** 書くと4台とも同じキーになってしまうため、
`start-servers.ps1` が起動時に `--key` で1台ずつ渡しています。
1つのキーが漏れても、他の3環境は読めません（実際にそうなることを確認済み）。

## 文書の投入

```powershell
venv\Scripts\python.exe ingest.py            # 4環境ぶん全部
venv\Scripts\python.exe ingest.py trouble    # 1環境だけ
```

`docs/` の下にワークスペース名のフォルダがあり、その中の `.md` を投入します。

```
docs/
  manual/     → 設備マニュアル（9621）
  trouble/    → トラブル事例（9622）
  kaizen/     → 改善事例（9623）
  standard/   → 作業標準（9624）
```

**文書を足したいとき**は、該当フォルダに `.md` を置いて `ingest.py` を実行し直すだけです。
既に入っている文書はサーバが 409 を返すので、スクリプトが「済み」として飛ばします。
**新しい文書だけが入る**ので、何度実行しても二重にはなりません。

```
■ 設備マニュアル（port 9621 / workspace manual）— 文書 4 件
    新規 1 件 / 済み 3 件 / 失敗 0 件
    索引作成を待ちます…
    完了: processed:4
```

**文書を差し替えたいとき**は、先にサーバの管理画面（`http://127.0.0.1:9621` など）から
その文書を削除してください。`ingest.py` は上書きしません。

投入すると LightRAG が **OpenAI を使って**エンティティと関係を抽出し、
ナレッジグラフとベクトル索引を作ります。ここで費用がかかります（`.env` の
`LLM_MODEL` / `EMBEDDING_MODEL`。検証用に安いモデルを選んであります）。
同梱の14文書ぶんは既に投入済みです。

## 試せる質問

4つのナレッジベースは互いに関連づけてあるので、**環境をまたぐ質問**が試せます。

| 質問 | 期待される動き |
|---|---|
| A装置のセンサー交換の手順を教えて | 設備マニュアルだけで答える |
| A装置のMTTRが8月に悪化した原因は？ | トラブル事例（事例152・139）＋ 改善事例087 を突き合わせる |
| MTTRに保全の待ち時間は含める？ | 作業標準（STD-102）を引く |
| B装置の改善は、なぜMTTRでは評価できない？ | 改善事例092 の「件数×時間で見る」を引く |
| 交換周期を過ぎた部品で止まった事例と、その対策は？ | トラブル事例152 ＋ 改善事例079 ＋ 作業標準103 |

DBを取り込んであれば、**「8月のMTTRをDBから出して、原因を文書から調べてExcelに」**のように
SQLと文書をまたぐ依頼も試せます。

## 設定

`.env` が4台共通の設定です。**OpenAI の APIキーが平文で入っています**（`.gitignore` 済み）。

| 項目 | 値 | 意味 |
|---|---|---|
| `LLM_MODEL` | `gpt-4.1-nano` | 索引作成のエンティティ抽出、検索時のキーワード抽出 |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | ベクトル検索の埋め込み（次元1536） |
| `MAX_ASYNC` | 4 | 索引作成の同時実行数。上げるとレート制限に当たりやすい |

> **aiagent 側の `env`（ドット無し）とは別物です。**
> アプリのほうは「隠しファイルだとエクスプローラで見えない」という理由で
> ドット無しに統一していますが、LightRAG 本体は `.env` しか読みません。
> 読み先はソースにハードコードされていて変えられず、さらに **`.env` が無いと
> 対話プロンプトを出して起動しません**（`utils_api.py` の `check_env_file`）。
> ここは LightRAG の流儀に合わせています。

### モデルの選び方

`gpt-4.1-nano` は検証用に費用を抑えるための選択です。実際に4モデルを試した結果:

| モデル | temperature | 簡単な抽出の出力トークン | 判定 |
|---|---|---|---|
| `gpt-4.1-nano` | 受け付ける | 3 | **採用**。非推論モデルで最も安い |
| `gpt-4o-mini` | 受け付ける | 3 | 動くが 4.1-nano より高い |
| `gpt-5-nano` | **拒否（400）** | 332 | 使えない。下記参照 |
| `gpt-5.4-nano` | 受け付ける | 5 | 動くが抽出の精度が落ちた |

`gpt-5-nano` が使えないのは2つの理由からです。**LightRAG は `temperature` を送る**ので
400 で落ちること、そして**推論トークンを吐く**ため、簡単な抽出でも出力が
数百トークンに膨らみ、単価が安くても請求は高くつくこと。

抽出の精度を上げたくなったら `gpt-4.1-mini` か `gpt-4o-mini` に上げてください。
**LLM を変えても、作成済みの索引はそのまま使えます**（作り直し不要。
変わるのはこれから投入する文書の抽出と、検索時のキーワード抽出だけ）。

埋め込みモデルは別で、**変えると索引の作り直しが必要**です（次元が変わるため）。
`rag_storage/` を消してから `ingest.py` を実行し直してください。
`text-embedding-3-small` はこのキーで使える3つのうち最も安いものです。

## 実運用に移すとき

このフォルダは検証用です。本番では次が変わります。

| 項目 | 検証（ここ） | 本番 |
|---|---|---|
| サーバの場所 | 手元のPC（127.0.0.1） | IT部門が用意したサーバ |
| URL | `http://127.0.0.1:962x` | `https://rag.example.co.jp/...` |
| APIキー | このREADMEに書いてある | IT部門から払い出される |
| 誰が立てるか | あなた | IT部門 |

**アプリ側の変更は要りません。** 管理画面で登録した4件を削除し、
払い出された URL とキーを入れ直すだけです。
HTTPS・リバースプロキシ配下（`/lightrag` のようなパス付き）・社内プロキシ経由も、
アプリのクライアントがそのまま扱えます。

## 困ったとき

| 症状 | 見るところ |
|---|---|
| `check-servers.ps1` が「応答なし」 | 起動直後は20〜40秒かかる。それ以上なら各サーバのウィンドウ（最小化されている）を見る |
| 「キーNG」 | `start-servers.ps1` の Key と、アプリに入れたキーが一致しているか |
| 検索が0件で返る | `ingest.py` を実行したか。`check-servers.ps1` の文書件数を確認 |
| 索引作成が進まない | OpenAI のキーが有効か。`.env` の `LLM_BINDING_API_KEY` |
| ポートが使われている | `stop-servers.ps1` で止めてから起動し直す |
