# インシデント対応フロー

所管: 情報システム部　更新: 2026年10月

## 1. インシデントの区分

| 区分 | 定義 | 目標復旧時間 |
|---|---|---|
| **P1 重大** | 全社または基幹システムが停止。業務が完全に止まる | **2時間** |
| **P2 高** | 部門単位で業務に支障。代替手段がない | **4時間** |
| **P3 中** | 一部機能が使えない。代替手段がある | **1営業日** |
| **P4 低** | 軽微な不具合・問い合わせ | **3営業日** |

**区分は「困っている人数」ではなく「業務が止まるか」で決めます。**
1人でも基幹業務が完全に止まれば P2 です。

## 2. 対応の流れ

    受付 → 区分の判定 → 一次対応 → 原因調査 → 恒久対策 → 記録

### 受付
チャット・内線・メールのいずれでも受け付けます。
**受付時刻を記録**します（目標復旧時間の起点）。

### 一次対応
**まず業務を戻すこと**を優先します。原因の特定は後でよい。
再起動・切り替え・代替手段の案内など、早く動くものを選びます。

### 原因調査
業務が戻ってから、落ち着いて調べます。
**P1・P2 は必ず原因を特定し、報告書を作成**します。

## 3. エスカレーション

| 状況 | エスカレーション先 |
|---|---|
| P1 発生 | ただちに情報システム部長＋経営層へ第一報 |
| 目標復旧時間の半分を過ぎた | 情報システム部長 |
| 外部要因（回線・クラウド障害） | ベンダーへ連絡し、状況を随時共有 |

**「もう少しで直りそう」で報告を遅らせない。**
遅れた報告がいちばん問題になります。

## 4. 記録

すべてのインシデントを記録します。記録項目は次のとおり。

- 受付日時・復旧日時（**この差が復旧時間**）
- 区分（P1〜P4）
- 事象・影響範囲
- 一次対応の内容
- 原因
- 恒久対策

## 5. 再発防止

**同じ事象が3か月に3回以上**発生した場合、恒久対策を必須とします。
「再起動で直る」を繰り返すのは対応ではなく先送りです。

## 6. 変更作業との関係

インシデントの多くは**変更作業の直後**に起きます。
変更は原則として**業務時間外**に行い、**切り戻し手順**を用意してから実施します。
